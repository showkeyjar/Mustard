基线: v21 全量 13 类，3641 样本，MICRO 74.32%，失败 935

|---|---|---|---|---|

`llm_selected→verified` 一条路径占了全部失败的 45.3%。作为对照，
当前排在候选队列里的 arg_missing_suffix 只有 83 例。

irrelevance 两类合计 270 样本、233 个失败。

## 机制

`carm_bfcl_server_optimized.py` 里有两种问法，用的是同一个模型：

- line 4009 `LLM selected: [...]` → 直接进入 `Verified:`，**没有确认步骤**
- line 4311 `LLM confirmed relevance` / 4313 `LLM rejected ... as irrelevant → []`

前者问的是"**哪个**函数合适"，这个问法预设了存在合适的函数；
后者问的是"这个函数**是否**相关"，允许回答否。

`fb_nomatch`（LLM 明确回答没有匹配）准确率 99.4%，说明模型在被允许说"否"时
判断是可靠的。问题出在问法，不在模型能力。

## 猜想（尚未验证）

把 4311/4313 已有的确认步骤接到 4009 这条路径后面。
不是新机制，是把现成的步骤补到漏掉它的分支上。

## 为什么现在不能做

1. **选择效应。** 走 `llm_selected` 的前提是信号分数低于阈值，
   难样本天然集中在这里。56.2% 的准确率有多少来自路径缺陷、
   多少来自样本难度，这张表回答不了。

2. **收益上界与下界都没算。** 同一个桶里 `live_multiple` 有 553 样本、
   388 个判对。确认步骤每误拒一个就是净亏。
   理论收益区间是 [-388, +233]，正负号完全取决于确认步骤的精度 ——
   而这个精度目前是零测量。

3. **离线复现必须先校验保真度。** 要估收益就得离线重放 969 次确认调用。
   这正是"代理指标"，必须先拿真实系统输出逐样本比对、报告一致率，
   一致率不足就不得据其下结论。BFCL 路由优化上已经在这一步栽过一次
   （离线镜像与生产二元一致率仅 55%，三个候选方案全部作废）。

## v23 执行顺序（每步产出证据后才进入下一步）

1. 导出 v21 里 `llm_selected→verified` 的全部 969 个样本及其上下文。
2. 用生产代码里的确认函数逐样本重放，**先在已知结论的子集上校验保真度**，
   报告与生产的二元一致率。一致率不达标就停在这里。
3. 保真度过关后，统计确认步骤在这 969 个样本上的拒绝率与拒绝精度，
   算出真实收益区间。
4. 收益为正且区间下界可接受，才写事前承诺清单，然后走契约测试部署。

## 一条方法论记录

这份分析的第一版把最大失败桶归错了位置：分类器里的 marker 字符串
`"LLM fallback selected"` 是凭印象写的，那条分支实际一次都没触发，
于是整张表显示"llm_fallback 0 样本"，差点得出"这条路径不存在问题"的结论。
改成从源码逐条抄 `logger.info` 字符串、并统计完整决策序列之后，
真实的最大失败桶才浮出来。**日志 marker 必须从源码核对，不能凭记忆写。**
