## Phase 1.5：风险缓解与防御加固（待执行 🔧）

> 目标：防止 Phase 1 修复引入新误判，加固边缘场景

- [ ] **1A-防御：低意图短查询的 search 体验优化**
  - 优先级：中 · 预估：~10 行 · 风险：低
  - 做什么：在 SearchTool 中添加最短查询长度检查（如 <3 字且无上下文时返回 "请补充更多信息" 提示）
  - 为什么："嗯"/"分析" 等极短查询路由到 search 可能产生无意义搜索结果
  - 相关失败：d106 "嗯"、d110 "分析"
  - 验收标准：短查询不返回空白或无关搜索结果

- [ ] **2A-防御："还是" 口语排除词**
  - 优先级：低 · 预估：~5 行 · 风险：低
  - 做什么：在 `is_conflict_task` 或 compare 检测中添加排除模式——"还是算了吧"/"还是别"/"还是不" 等口语不触发
  - 为什么："还是" 加入 COMPARE_TOKENS 后，可能误匹配 "还是算了" 等口语表达
  - 验收标准："还是算了吧" 不触发 compare 信号；"A还是B" 技术选型仍正常触发

- [ ] **3A-防御：合成 vs 搜索边界用例补充测试**
  - 优先级：中 · 预估：新增 5-8 条评测 prompt · 风险：低
  - 做什么：在 diverse_eval.json 中补充边界用例：
    - "比较两个方案并总结" → bigmodel_proxy（有强合成动词）
    - "比较A和B哪个好" → search（无合成动词）
    - "先搜资料再总结" → search（先搜后合）
    - "信息够了，比较一下给出结论" → bigmodel_proxy（已搜+合成）
  - 为什么：compare 和 synthesis 的边界是最容易出回归的地方
  - 验收标准：补充用例全部路由正确，原有 205 条无回归

## Phase 2：评测体系升级（待规划 📋）

> 目标：解决 "开发者自标注" 的确认偏差问题，建立可信的评测基准

- [ ] **评测集扩展到 500+ 条**
  - 优先级：高 · 预估：2-3 天 · 风险：低
  - 做什么：将 diverse_eval.json 从 205 条扩展到 500+ 条，覆盖更多边缘场景：
    - 多语言混合（中英夹杂）
    - 错别字和口语化表达
    - 超长查询（>200 字）
    - 嵌套意图（"先A再B最后C"）
    - 反讽/反问句式
  - 为什么：205 条覆盖面有限，100% 准确率不代表真实表现
  - 验收标准：500+ 条 prompt，每类意图至少 50 条，边缘场景 >30%

- [ ] **独立标注 expected_tool**
  - 优先级：高 · 预估：1-2 天 · 风险：中（需要外部人员）
  - 做什么：找 2-3 名不了解 CARM 设计的开发者独立标注 500 条评测集的 expected_tool，取多数投票结果
  - 为什么：当前 205 条由 CARM 开发者标注，存在确认偏差（标注者知道 CARM 的设计哲学）
  - 验收标准：独立标注与当前标注的一致率 >85%，不一致的条目人工裁定

- [ ] **引入轻量分类器（规则 → 混合路由）**
  - 优先级：中 · 预估：3-5 天 · 风险：中
  - 做什么：在规则层和语义编码器之间增加一个轻量分类器（如 logistic regression 或 2 层 MLP），用信号特征作为输入，在语义编码器之前做一层拦截
  - 为什么：16 条失败中有 3 条是因为无信号匹配落入语义编码器后选错。规则有盲区，语义编码器不够准，中间需要一层
  - 技术方案：
    - 特征：所有信号函数的布尔输出（~30 维）
    - 模型：sklearn LogisticRegression 或 2 层 MLP（<200 参数）
    - 训练数据：500 条标注集 + 历史失败案例
    - 部署：作为 hard_rule 和 semantic 之间的 L2 层
  - 验收标准：在 500 条独立标注集上，混合路由准确率 > 纯规则 > 纯语义

## Phase 3：生产验证与能力扩展（待规划 🚀）

> 目标：接入真实流量验证，扩展多轮上下文能力

- [ ] **真实用户流量 A/B 测试**
  - 优先级：高 · 预估：5-7 天 · 风险：高（需接入生产）
  - 做什么：
    1. 在 router 中添加 "路由后用户手动切换工具" 的隐式反馈采集
    2. 设计 A/B 实验：A 组 = 当前规则路由，B 组 = 混合路由
    3. 以 "用户切换工具率" 作为核心指标（越低越好）
    4. 统计显著性检验（p < 0.05 且绝对提升 > 2%）
  - 为什么：评测集准确率再高也不如真实用户反馈可信
  - 验收标准：B 组切换率显著低于 A 组，或至少无显著劣化

- [ ] **多轮对话上下文路由**
  - 优先级：中 · 预估：3-5 天 · 风险：中
  - 做什么：
    1. 在路由器中引入会话记忆，用前序轮次的意图推断当前轮次的隐含意图
    2. 低意图查询（"嗯"/"不是那个"/"继续"）根据上一轮意图推断
    3. "它"/"那个"/"这个" 等指代消解
  - 为什么：d106 "嗯"、d108 "不是那个" 这类低意图查询在多轮对话中其实有明确含义
  - 验收标准：多轮对话场景下，低意图查询的路由准确率 > 80%（人工评估）

- [ ] **与 GPT-4 / Claude 3.5 对比**
  - 优先级：低 · 预估：1 天 + API 成本 · 风险：低
  - 做什么：用 GPT-4o 或 Claude 3.5 Sonnet 跑 205 条 zero-shot 工具选择，与 CARM 对比
  - 为什么：当前对比用 gemma3:12b（12B 参数），非 GPT-4 级别，说服力有限
  - 验收标准：产出对比报告，包含准确率、失败模式分析、成本对比
