# Mustard 修改与优化建议

## 1. 核心判断

Mustard 不建议继续把主要目标定义为“训练一个更强的 Compact Agentic Reasoning Model”。

建议将研究重心从：

> Learning Reasoning

升级为：

> **Learning How to Reason → Learning How to Execute → Learning Its Own Harness**

最终定位为：

> **Self-Harness / Adaptive Cognitive Runtime**

核心研究问题：

> Agent 能否根据任务、执行反馈和历史经验，自动选择、修改和优化自己的执行机制（Harness），并在后续未见任务中获得可验证的性能提升？

---

## 2. 为什么需要调整

当前 Harness Engineering 的快速发展说明：Agent 能力不仅来自 Base Model，还来自：

- Context strategy
- Memory strategy
- Tool selection
- Planning
- Reasoning mode
- Verification
- Retry / recovery
- Permission / governance
- Observability

因此，固定 Harness 的 Agent 可以进一步演化为：

```text
Task
 ↓
Meta-Controller
 ↓
选择 Harness
 ↓
Reasoning / Tool / Memory / Execution
 ↓
Environment
 ↓
Evaluation
 ↓
Harness Update
 ↓
下一任务
```

Mustard 最值得研究的不是“更强的固定 Agent”，而是：

> **模型如何决定自己应该以什么方式工作。**

---

# 3. 建议的新定位

## 3.1 项目定位

**Mustard = Self-Harness / Adaptive Agent Runtime**

可以继续保留 CARM（Compact Agentic Reasoning Model）作为模型/实验载体，但不要让“模型规模和 benchmark 分数”成为项目唯一核心。

建议研究主题：

> **Adaptive Cognitive Runtime for Self-Harnessing Agents**

---

## 3.2 核心研究问题

Mustard 应重点回答：

1. Agent 能否识别当前任务适合什么执行策略？
2. Agent 能否从执行失败中发现 Harness 层面的缺陷？
3. Agent 能否自动生成或修改 Harness Policy？
4. 修改后的 Harness 是否真的提升后续任务成功率？
5. 这种提升是否能迁移到未见任务？
6. Agent 是否能避免因自我修改造成能力回归？
7. Harness 学习的成本是否低于直接扩大模型或人工工程？

---

# 4. 架构建议

当前已有 reasoning kernel、working memory、tool bus、PLAN/HYP/DRAFT、tool routing、experience replay、online evolution 等能力，应尽量保留。

新增一个明确的一等对象：

```python
HarnessPolicy(
    reasoning_mode="hypothesis_first",
    context_strategy="progressive",
    memory_strategy="episodic",
    tool_strategy="search_then_code",
    verification="dual_check",
    retry_policy="bounded",
    exploration=0.35,
)
```

整体结构建议：

```text
                         Task
                           ↓
                  ┌─────────────────┐
                  │ Meta-Controller │
                  └────────┬────────┘
                           ↓
                    Harness Policy
                           ↓
        ┌──────────────────┼──────────────────┐
        ↓                  ↓                  ↓
    Reasoning           Memory             Tools
        ↓                  ↓                  ↓
                    Execution Loop
                           ↓
                       Environment
                           ↓
                       Evaluation
                           ↓
                  Failure Attribution
                           ↓
                  Harness Modification
                           ↓
                    Harness Library
```

---

# 5. Harness Policy 应该成为核心研究对象

传统 Agent：

```text
Task → Action
```

Mustard 应研究：

```text
Task → Harness → Action
```

进一步：

```text
Task
 ↓
Harness A
 ↓
Execution
 ↓
Reward = 0.71

Harness B
 ↓
Execution
 ↓
Reward = 0.83

Harness C
 ↓
Execution
 ↓
Reward = 0.88
```

最终学习：

> **Harness Selection Policy**

即：

> 什么任务应该采用什么认知/执行结构。

---

# 6. Harness 不应只是 Prompt

建议将 Harness 抽象为多个可组合维度：

```text
Harness
├── reasoning policy
├── context policy
├── memory policy
├── tool policy
├── planning policy
├── verification policy
├── retry/recovery policy
├── exploration policy
└── governance policy
```

这样才能避免项目退化成“自动 Prompt Engineering”。

---

# 7. 最重要的研究闭环

必须形成：

```text
Task
 ↓
Harness Selection
 ↓
Execution
 ↓
Observation
 ↓
Evaluation
 ↓
Failure Attribution
 ↓
Harness Modification
 ↓
Re-execution
 ↓
Generalization Test
```

其中最关键的是：

> **Evaluation + Failure Attribution**

因为“能够修改自己”并不意味着“修改后变好了”。

---

# 8. Benchmark 不应只追求绝对分数

不建议把研究目标变成：

> Mustard 在 BFCL/SWE-bench/Terminal-Bench 上超过谁。

更有价值的是定义：

## Self-Harness Evaluation Protocol

核心指标：

### 8.1 Initial Capability

```text
P_before
```

初始任务成功率。

### 8.2 Adaptation Gain

```text
ΔP = P_after - P_before
```

经历失败/经验以后，性能提升多少。

### 8.3 Learning Efficiency

```text
Learning Efficiency
= Performance Gain / Experience Episodes
```

### 8.4 Transfer Gain

在学习任务之后测试未见任务：

```text
Learning Tasks
       ↓
Harness Adaptation
       ↓
Unseen Tasks
```

这是必须重点关注的指标。

### 8.5 Retention

学到的 Harness 是否长期有效。

### 8.6 Regression

自我修改是否破坏已有能力。

### 8.7 Cost

比较：

- Token
- latency
- tool calls
- memory
- compute

---

# 9. 建议建立 Harness Learning Curve

横轴：

> Experience / Episodes

纵轴：

> Task Success

比较：

- Static Agent
- Static Harness
- Self-Harness
- Self-Harness + SIM

重点观察：

> Agent 是否随着经验增加而持续提升。

真正要证明的不是：

> “Agent 很强”

而是：

> **“Agent 会成长，而且成长具有迁移性。”**

---

# 10. 建议使用现有 Benchmark，而不是马上重新造大型 Benchmark

第一阶段可以基于：

- BFCL
- Terminal-Bench
- SWE-bench
- GAIA
- 其他适合工具调用/执行任务的 benchmark

重新设计实验协议：

```text
Baseline Tasks
      ↓
Learning Tasks
      ↓
Harness Adaptation
      ↓
Transfer Tasks
```

这样既有社区认可的 benchmark，又能测量 Self-Harness。

---

# 11. 建议的最小实验

第一阶段只回答三个问题：

### Q1
Agent 能否从失败中自动修改 Harness？

### Q2
修改后的 Harness 是否提高后续任务成功率？

### Q3
这种提升能否迁移到未见任务？

如果三个答案均为 Yes，就已经形成非常有价值的研究结果。

---

# 12. Ablation 设计

建议至少比较：

```text
A. Base Agent
B. Agent + Static Harness
C. Agent + Memory
D. Agent + Experience Replay
E. Agent + Self-Harness
F. Agent + SIM
G. Agent + SIM + Self-Harness
```

重点观察：

- Initial Performance
- Adaptation Gain
- Transfer Gain
- Retention
- Regression
- Cost

---

# 13. Mustard 与 SIM 的接口

两个项目不应简单合并。

建议：

```text
SIM
 ↓
判断什么经验值得内化
 ↓
生成 Candidate Capability
 ↓
Mustard
 ↓
将 Capability 转化为 Harness / Policy
 ↓
执行
 ↓
Evaluation
 ↓
SIM 再判断是否值得保留
```

因此：

> SIM 负责“学什么”
>
> Mustard 负责“怎么用”

---

# 14. 建议增加 Harness Capability Registry

例如：

```text
Harness Registry

coding/
  diagnose_then_patch
  test_first
  regression_loop

research/
  evidence_first
  search_then_synthesize
  cross_validate

data/
  inspect_then_transform
  validate_before_export

scientific/
  hypothesis_first
  experiment_then_verify
```

Harness 不应该只是一次性的动态产物，也可以沉淀为可复用能力。

---

# 15. 不建议做什么

## 不建议 1：继续无限扩充 Agent 功能

例如不断增加：

- 新工具
- 新 memory
- 新 planner
- 新 prompt
- 新 agent mode

如果没有进入 Self-Harness 闭环，价值有限。

## 不建议 2：过早追求大模型训练

不要把项目变成：

> CARM vs Qwen vs Llama vs Gemma

重点不是训练一个更大的模型，而是研究：

> **模型如何学习自己的运行机制。**

## 不建议 3：只追求单一 benchmark 分数

单一 benchmark 无法证明 Self-Harness。

## 不建议 4：把 Self-Reflection 当成 Self-Harness

```text
Answer → Critique → Improve
```

只是 output-level reflection。

真正的 Self-Harness 是：

```text
Task
 ↓
选择 reasoning / memory / tool / verification strategy
 ↓
执行
 ↓
发现问题
 ↓
修改 execution architecture
```

---

# 16. 推荐的发展路线

## Phase 0：研究问题收敛

明确：

> Mustard 研究 Agent 如何学习和优化自己的 Harness。

## Phase 1：Harness Policy

增加：

- HarnessPolicy
- Harness Registry
- Harness Selection

## Phase 2：Harness Adaptation

实现：

```text
Failure
 ↓
Attribution
 ↓
Candidate Harness
 ↓
Evaluation
 ↓
Accept / Reject / Rollback
```

## Phase 3：Benchmark Protocol

基于 BFCL / Terminal-Bench 等构建：

- Baseline
- Learning
- Transfer
- Retention
- Regression

## Phase 4：与 SIM 集成

测试：

> SIM 是否能够帮助 Mustard 更有效地选择哪些经验值得转化为 Harness。

## Phase 5：开放实验

提供：

- benchmark
- logs
- trajectories
- Harness versions
- reproduction scripts

让第三方复现。

---

# 17. 最终研究目标

最终不要把 Mustard 描述成：

> 一个更强的小型 Agent。

而应逐渐形成：

> **一个能够根据任务和经验动态选择、修改、验证自身 Harness 的 Adaptive Cognitive Runtime。**

最终闭环：

```text
Experience
    ↓
Failure / Surprise
    ↓
Harness Diagnosis
    ↓
Harness Modification
    ↓
Execution
    ↓
Evaluation
    ↓
Transfer
    ↓
Harness Consolidation
    ↓
Future Tasks
```

这就是 Mustard 最值得形成的独特研究标签。
